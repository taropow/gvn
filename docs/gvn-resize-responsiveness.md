# ウィンドウのリサイズ応答（0.76.0）

普段の快適さ、とくにウィンドウ枠をドラッグしたときの追従を優先する。専用ブランチ `codex/daily-responsiveness` で、配布済み0.75.0を保持して比較する。

## 処理

- リサイズ中に続けて届いた `WM_SIZE` は最新のサイズへまとめる。次の `WM_PAINT` の前に配置・状態を更新し、ドラッグ中も描く。終了・取消・明示的な描画や画像取得でも残った配置を反映する。待機タイマーは追加しない。
- Direct2Dの描画先は、配置だけで毎回リサイズせず、次の描画で最新のクライアント寸法へ合わせる。サイズ変更後は内容保持に頼らず全面を描く。
- 非表示のキャンバススクロールバーは移動しない。表示されるときに最新の寸法へ配置する。1行のツールバー本体はボタンが並ぶ幅にし、残る空白はホスト側で描く。横幅を変えてもボタンが収まっている間は本体のサイズを変えない。
- ツールバーが1行で、表示項目と収まる範囲が同じなら、ネイティブの行配置を繰り返さない。狭い幅、項目の出し入れ、複数行、DPI・テーマ・密度・文字列変更では再計算する。
- 表示済みタイルを使うリサイズ中のプレビューを、中小画像にも適用する。縮小済みタイルを拡大縮小して描き、元画像全体のBGRAコピーを避ける。手動ズームなどで新しく見える部分が既存タイルの外なら、完全な画像を表示できる経路へ戻す。画像とフレームが一致する場合だけ再利用する。
- 操作終了後は指定した無補正・高速・高画質へ戻す。元のRGBA、透明画素内RGB、選択範囲や編集内容を変更しない。明示的な画面取得は従来どおり独立して描く。
- 枠のドラッグ中は、同じ子コントロール全体へのIME方針の再適用を省く。コントロール作成・フォーカス・入力言語変更への適用は継続し、操作終了・取消時にも適用する。

## 検証の範囲

ユーザーの画像・設定・クリップボード・起動中のウィンドウを使わず、専用の非対話デスクトップと所有するテストプロセスで行う。ComputerUseは使用しない。ネイティブのサイズ変更と実際のDirect2D描画を測るが、物理的なマウス入力、モニターへの提示、DWM合成までの遅延は測っていない。

`tests/resize_app_cases.inc` の同一測定を改善前・後の実行ファイルで交互に実行する。UI更新だけを測る条件はサイズ変更の集約を含み、最終配置は測定区間の後にも行われるため、全体の速さの根拠にはしない。描画込みの条件には各サイズで配置と描画を含む。合否を短い時間の固定しきい値に依存させない。



| 描画込みの条件 | 0.75.0 → 0.76.0（ms／回） |
| --- | --- |
| 画像・横方向 | 18.58 → 9.46 |
| 画像・縦方向 | 10.94 → 6.21 |
| 編集モード・横方向 | 18.14 → 14.20 |

同じ2048×1536 RGBA画像をフィット表示し、各版3試行、1試行3ブロック×20サイズ変更の中央値。各試行で旧版・新版の順序を交代した。実行環境による変動があり、画面提示までの時間やすべての画像への高速化率ではない。

リサイズ中の元画像全体の表示用コピーは、この試料で12,582,912 → 0バイト。横方向の閲覧条件ではツールバーの行配置要求が60 → 0回になった（初期表示・オーバーフローの切替時は再配置する）。

関連アプリ14件、表示33件、専用自動操縦4本219操作・16画面、配布EXE主要10経路が通過した。表示33件は、変更のない描画ソースと実行ファイルの一致を確認して成功結果を再利用した。

[測定値](verification/0.76.0-resize-responsiveness/final/measurements.json)、[確認記録](verification/0.76.0-resize-responsiveness-related.json)。普段使い用 `G:\gvn\app\gvd.exe` は0.76.0へ差し替え済み。既存ウィンドウは保持し、次の起動から新しい版を使う。

# 先読みと画像キャッシュ（0.10.4）

頻繁な利用と多重起動のため、各ウィンドウに残すデコード済み画像を予算内へ抑える。画像を閉じた後や編集画像へ置き換えた後にも、ファイル用キャッシュを解放する。

## 設定

「設定 → ファイル読み込み」の下部に次の項目を置く。項目が隠れている時はページを下へスクロールする。

| 項目 | 既定値 | 動作 |
| --- | --- | --- |
| 隣の画像を先読みする | ON | 表示後に次、前の順で隣接画像を準備する。OFFは新たな先読みを止め、予算内の既存キャッシュは再利用する |
| 画像キャッシュ容量 | 64MiB | 0〜4096MiB。0はキャッシュと先読みを無効にする |

INIは`[Viewer] prefetch_enabled / cache_mib`。旧INIにない場合も64MiB・ONになる。適用・キャンセル・保存/再読込・読み込みページのリセットを検査する。これらはGVNの追加設定で、MassiGraの参照191行を実装済みへ増やすための項目として数えない。

## 保持と読み込みの規則

表示中の画像を優先し、先読みでキャッシュから追い出さない。次の画像を優先して準備し、残りの予算に収まれば前の画像も準備する。同じ先読みの組の中で、後から前画像が来たために準備済みの次画像を追い出すことを防ぐ。次の表示で新しい組へ進むと、古い非優先画像から解放する。

既定の64MiBでは、3840×2160 RGBA画像2枚が約63.28MiBで収まる。表示画像だけで予算を超える場合は、通常表示を許し、その間の先読みを止める。キャッシュ外にある保存済み編集画像・クリップボード画像の表示容量も、先読みを再開する際に予約する。既存画像をコピーしてキャッシュへ戻すための容量は確保しない。

先読みは、優先画像分を除いた残りをデコード上限にする。入力ファイルやZIPの読み込み・展開にも同じ予算を渡し、予算に収まらない先読みは省略する。容量が不足しただけの先読みでエラー画面を出さない。通常の「開く」は、従来のデコード上限256MiB、入力上限512MiB、ZIP項目の入力上限256MiBを維持する。PSD、GIF、APNG等を先読み予算のために通常表示から除外しない。

この予算は画像モデルの保持量で、アプリ全体のメモリ上限ではない。圧縮入力、ライブラリの作業領域、表示タイル、描画先、Undo、切り替え中の旧画像等は別に必要になる。設定適用と解放はワーカーで行い、現在のライブラリデコードが終わった後に反映する。実行中のデコードを強制中断していないため、適用直後や切り替え中の瞬間値と、完了後の保持量を区別する。

## キャンセルと解放

新しい読み込みを優先し、不要になった古い結果を表示やキャッシュへ戻さない。同じパス・読み込み設定の先読みが進んでいる場合は、その結果を後続の通常読み込みへ再利用する。強制再読み込みは再デコードする。

画像を閉じると、先読み待ちと読み込み要求を取り消し、キャッシュと表示画像・Undoを解放する。編集中の画像や貼り付け画像へ置き換える場合も、旧ファイルのキャッシュを解放する。編集中のUndo自体は「Undoを有効にする」の設定に従う。遅れて終了した先読みが、解放後のキャッシュを復活させないことも検査する。

## 検証

ローダー試験は予算・優先順位、容量変更、無効化、予算を超える表示画像、キャッシュ外の表示画像、キャンセル中の解放、同一先読みの再利用、読み込み設定の識別、見開き、失敗後の復帰を含む。実際のPNG/BMP/PSD/GIF/APNGとZIPでも、小さな先読み上限での拒否と通常読み込みの成功を組にして確認する。

実Appの統合試験は画像を置き換えずに容量を変更できること、キャッシュからの次画像、閉じた後の解放を確認する。専用自動操縦25は実設定画面のスクロール、範囲エラー、ON/OFF、0/1/64MiB、保存、リセット、キャンセル、RGBAコピーと閉じた後を通す。既存の読み込み設定シナリオ18も維持する。

`wait_cache`は表示要求だけでなく先読みと解放の完了を待つ専用操作で、通常のUIでは待機しない。診断JSONの`cache_bytes`は保持画像の計数、`cache_limit`は適用済み予算、`cache_idle`はワーカーと待機処理が空であることを示す。`prefetch_loads`は容量不足等で中止した試行も含み、正常なデコード件数ではない。

負荷試験は合成4K JPEGを12の異なる名前へ複製し、自分が起動した隠しGVNのPIDとHWNDだけに次画像コマンドを送る。全画像名を確認し、待機後のプロセスメモリと最終2秒待機後の値を記録する。既存のGVN、ユーザーのクリップボードと設定、MassiGraは操作しない。タイトルとUI応答による時間は観測上の目安で、実モニタ提示や厳密な描画完了の時計として扱わない。

## 最終版の負荷試験

配布済み0.10.3と最終0.10.4を、同じ生成3840×2160 JPEGで比較した。各3回、旧/新の実行順を交互にする。OSキャッシュは消去せず、通常サイズの隠しウィンドウと既定Linearを使う。12枚は同じ画像の異なるファイル名であり、実写真全般や多形式の一般値ではない。

連続12枚を順番に開いた後、2秒待機したプライベートメモリ中央値は269.70→79.41MiB、削減率は70.56%。12枚目の150ms待機後に採取した、その時点までのOSピークワーキングセット中央値は322.97→133.24MiBだった。ピークワーキングセットには切り替え中の一時確保と共有ページを含む。ピークのプライベートメモリとは呼ばない。

| 進行位置・待機後 | 0.10.3 | 0.10.4 |
| --- | --- | --- |
| 1枚目 | 75.45MiB | 75.49MiB |
| 4枚目 | 174.43MiB | 79.49MiB |
| 8枚目 | 269.68MiB | 79.50MiB |
| 12枚目 | 269.70MiB | 79.41MiB |

この表は各段階の150ms待機後の中央値で、上記の最終2秒待機後の値と採取時点が異なる。新しい最終レポートは保持画像66,355,200 bytes、上限67,108,864 bytes、先読み/解放完了を全3回で確認した。[全段階・全サンプル・ハッシュ](verification/0.10.4-navigation-memory/summary.json)を保存する。先行した機能確認1組も[別記録](verification/0.10.4-navigation-preliminary/summary.json)へ残し、最終3組の集計へ混ぜない。

別の比較では、12枚フォルダの中央の1枚を開き、隣接画像の先読み後に2秒待機した。連続12枚の巡回とは別条件である。各プロセスの採取値を合計し、同時ピークではない。

# 設定画面の応答時間

0.9.0での修正契約。ユーザーから、`dist/GVN-0.8.0`で設定画面を開くと10秒以上止まり、その後復帰したとの報告があった。既存の操作結果の試験に、画面を開く時間の検査が不足していた。

## 再現と原因

開発中の実設定コントロールを、非対話デスクトップの専用プローブで測定した。保存済みINIは読み取りのみで使い、ユーザーの設定は変更しない。修正前の生成は3回で4,243 / 5,781 / 4,053ms。工程別の別測定では7,307 / 9,694 / 7,531msで、全フィールド・キー一覧・マウス一覧の生成と、全ページの繰り返し配置に時間がかかっていた。ユーザーの0.8.0本体を直接計測した値ではない。

開いていない全16ページの入力欄、202機能のキー一覧、マウス割り当てを最初に生成していた。配置はタブ切替・スクロールのたびに非表示ページまで処理していた。個々のコントロールの作成、文字列追加、再配置・再描画がUIスレッドに集中していた。

## 修正

- ページのコンテナとスクロールバーも含め、最初は全般ページだけを生成する。他のページは最初に選んだときに作り、以降は同じHWNDと入力値を使う。
- 表示中のページだけを配置する。入力欄を移動するたびの再描画を避け、配置後にまとめて無効化する。
- キー一覧の複数行更新中は再描画を止め、更新後に戻す。
- 未生成ページは読み取らず、保持している設定値を適用する。未生成のキー・登録先・外部アプリ欄を空欄として扱わない。
- 未生成プレビューの無効化は省く。NULLのHWNDをInvalidateRectへ渡さない。

最初の修正後計測は同じINIで144 / 104 / 120ms。画面生成時間であり、実モニタの合成完了、他PC、全フォントの初回読み込みまでの保証値にはしない。各タブの初回生成は残るため、初回切替と再訪を別に測る。

## 起動時の設定読み込み

従来は約400項目で個別に`GetPrivateProfileStringW`を呼び、毎回32,768文字のバッファを確保していた。0.9.0では`GetPrivateProfileSectionW`で必要なセクションを一度ずつ読み、同じload内で使う。WindowsのINI解析と文字コード処理は継続し、セクションの大文字小文字、重複キーの先勝ち、引用符、空欄、既定値、長いセクションを従来APIの出力と照合する。キャッシュは1回のloadだけに限定し、外から変更したINIを次回に再読込する。極端に大きいセクションは従来の個別読込へ戻す。

読み取り専用の同じユーザーINIで、設定読み込みは修正直前225.28ms、修正後5.12msだった。専用プローブの部品計測であり、アプリ全体の起動時間やコールド起動の改善率には換算しない。画像指定の起動比較は[既存記録](gvn-navigation-benchmark.md)を残し、今回の変更後の起動比較は実施していない。

## 継続試験

`gvn_preferences_probe`とCTestの`preferences_responsiveness`で、実Win32の設定画面を3回生成する。初期表示で未選択ページの欄を作らないこと、初回全タブ切替、再訪、閉じる時間を記録する。生成1,500ms、全16タブの再訪合計3,000msを回帰検査の上限にする。

全般だけを変更・適用した時のINI全体を、期待値とバイト照合する。未表示の全画面補間、フォント、バー、キー、登録先、外部アプリ等が失われないことを確認する。表示ページの編集後に別タブを往復し、同じコントロールと未適用の値を保つこと、適用とキャンセルを別々に検査する。試験用INIだけを固有の一時フォルダへ作成する。

専用自動操縦の設定・キー・マウス・フォント・色・起動/バー・全画面・全補間の既存シナリオも回帰対象にする。確認結果の確定値とハッシュは[検証記録](gvn-verification.md)に保存する。ComputerUseや通常デスクトップの入力注入は使わない。

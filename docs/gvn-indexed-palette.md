## 0.48.0: 余白付き静止GIFの元パレットを保持

GIFの画像部分を論理キャンバスへ配置する時も、元のパレットと重複する色番号を保持する。背景が同色の別番号なら背景番号も保ち、透明な余白のRGBが元テーブルに無ければ新しい項目として追加する。元テーブルを変えずに追加できない場合と保持データが予算に入らない場合は、現在RGBAを維持して通常保存する。番号をRGBAから推測して再構成しない。

RGBAへ展開するだけでは、同じRGBを持つ別々のパレット番号を復元できない。0.13.0では表示用RGBAに加え、元のパレットとビット詰めの色番号を保持する。読み込み・加工・通常の保存画面を通す実装であり、保存用の減色APIだけとは区別する。

## 保持するデータ

`Frame::indexed`は読み取り専用の共有データ。幅、高さ、1/2/4/8ビット、RGBAのパレット、上位ビットから詰めた行データを持つ。1行は`ceil(幅×ビット数/8)`バイトで、行末の未使用ビットは画素として扱わない。同色の重複項目、未使用項目、パレットの透明・半透明も保持する。

PNG、通常BMP、全面の静止GIF/先頭コマは[WICのIndexed形式](https://learn.microsoft.com/en-us/windows/win32/wic/-wic-codec-native-pixel-formats)から元の番号を取得する。RGBAもその同じパレットから展開し、もう一度別の色変換をしない。RLE4/8 BMPはWICが番号を失う出力になるケースを実測したため、既存libplumを`PLUM_PALETTE_LOAD`で使う。重複をまとめたり番号を並べ替えたりするフラグは付けない。

1枚の保持量はRGBAの4バイト/画素に、ビット詰めの番号と最大1,024バイトのパレットを加えた値。`Image::bytes()`とキャッシュ予算に含める。読み込みの容量上限も保持データ全体に適用する。この値は作業中の一時バッファや、プロセスのワーキングセットの上限を意味しない。Undoやフレーム取り出しでは番号データを共有する。

## 読み込み設定と加工

アルファ保持が既定。透過無効や背景合成を選んだ場合はRGBAとパレットへ同じ変換を適用し、番号は変えない。

切り抜き、90度単位の回転、水平/垂直反転、最近傍リサイズでは番号も同じ座標変換を行う。フレーム取り出しは番号データを共有する。色調変更、ぼかし、透過合成による貼り付け、切り取り、滑らかなリサイズ等はRGBA画像へ移行して古いパレットを解除する。Undoは以前の画像と元番号を戻す。

保存時にも、保持したパレット/番号が現在のRGBAと一致することを確認する。RGBAを直接書き換えた呼び出しや壊れたメタデータが、編集後の画素を古い番号で上書きしないようにする。背景の市松や表示補間は保持画素と番号に影響しない。

## 通常の保存

PNGは一致するパレットがあれば、[PLTE/tRNS](https://libpng.org/pub/png/spec/iso/index-object.html)を使って元の1/2/4/8ビットと番号を保つ。アルファ保持では隠れたRGBも保つ。背景合成や透過色を指定した場合はパレット側へ同じ変換を適用する。圧縮、フィルタ、インターレースは引き続き設定できる。

BMPの色深度に「元の色深度（自動）」を追加した。既定は自動で、現在の番号が有効ならその色深度、2ビットは4ビットへ移す。RGBA画像は24ビット。1/4/8/24の明示指定も保持し、既存INIの明示値を勝手に自動へ変えない。RLEとトップダウンの規則は[保存契約](gvn-saving-options.md)に従う。

GIFも元番号が有効なら再減色せず再利用する。指定した透明番号の元RGBも残す。他の半透明色は背景合成となる。RGBAから減色する時は、共通のディザON/OFFも実際のGIF保存へ渡す。アニメの保存は選択した静止1コマのみ。

RLE4の奇数個の絶対モードで、Windows GDI+は正しい最終画素を返す一方、Pillow 12.0.0では一部が番号0になる例を検出した。同じ番号を表す「偶数個の絶対モード＋1画素の符号化モード」へ書き換え、読み手の差を避ける。書き換え後に通常BMPより小さくならなければ通常保存へ戻す。

## 残る範囲

16BPP BMPの明示保存は0.46、自動保存の555/565保持は0.47で[追加した](gvn-saving-options.md)。論理キャンバスに余白があるGIFや複数コマ合成GIFの元パレットは未完了。これらをRGBAから再減色した結果で「元番号を保持」とは扱わない。色を変える加工後の自動パレット再構成やパレット編集画面も、この保持処理だけで完成とはしない。設定S079とGOAL全体は継続する。

## 表示負荷の確認

完全なパレットではビットで表せる全番号が有効なので、形状の検査後に全画素の番号を再走査しない。部分的なパレットでは引き続き欠けた番号を検査する。RGBA展開は1/2/4/8ビットごとに分け、画素ごとの可変シフト/除算を減らした。全ビットが1の入力でも、完全なパレットなら有効、項目が欠けていれば無効となる境界も検査する。

3840×2160の合成PNGを1フォルダ1画像に分け、0.12.0と開発版を交互に各3回測定した。ファイルキャッシュが混在した通常環境での観測で、冷間起動やMassiGraとの比較ではない。

| 素材 | 表示完了ms（0.12.0 → 開発版の中央値） | プライベートメモリMiB（中央値） |
| --- | --- | --- |
| 1ビットパレット | 218 → 242 | 43.88 → 44.86 |
| 8ビットパレット | 256 → 233 | 43.58 → 51.50 |
| RGBA | 217 → 202 | 43.92 → 43.91 |

1ビットは番号保持が約1MiB、8ビットは約8MiB増える。RGBAには番号バッファを追加しない。時間にはばらつきがあり、上の値だけで速度改善率を主張しない。[全サンプルと計測スクリプト](verification/0.13.0-palette-performance/summary.json)を保持する。最初に3画像を同じフォルダへ置いた測定は先読み量が異なるため、[別の履歴](verification/0.13.0-palette-performance/mixed-folder/summary.json)として残し、保持処理だけの比較には使わない。

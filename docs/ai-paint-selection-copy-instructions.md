# AIへの実装指示書: 選択範囲のコピーに元の配置位置を付ける

あなたは、既存のWindows向け自作ペイントアプリを改修する担当AIです。既存の言語・フレームワーク・画像モデルに合わせて、以下を実装してください。仕様の提案だけで終えず、変更と必要な動作確認まで行ってください。

## 目的

矩形・折れ線・投げ縄などで選択した画像をコピーした時に、画像と一緒に「コピー元キャンバスのどこにあったか」をクリップボードへ保存する。対応する画像ビューアGVNへ渡し、元の座標へフローティング配置できるようにする。

**他の画像編集アプリへは、これまで通り画像として貼り付けられることが必須。独自形式だけへ置き換えない。**

GVN側の受信・バウンディングボックス・確定/中止は別担当の範囲である。今回の担当はペイントアプリのコピー側。共通形式の名前・ヘッダー・座標の意味を独自変更しない。

## 最初に確認する箇所

現在のコピー/Ctrl+C処理、選択範囲のマスク、キャンバスとレイヤーの座標変換、PNG/DIBのエンコード、Windowsクリップボード公開処理を調べる。既存の「見えている範囲をコピー」「レイヤーをコピー」等の違いと、既存の同アプリ内での貼り付け挙動を維持する。

## 必須の動作

1. 選択範囲の外接矩形で画像を切り出す。
2. 切り出した画像左上の、元キャンバスにおけるX/Yを記録する。
3. 元キャンバス寸法と、切り出し画像寸法を別々に記録する。
4. 選択範囲の外は透明にし、元画像の透明度と選択マスクの半透明を保持する。
5. 標準の画像形式を公開し、追加で位置付き独自形式を公開する。
6. コピー後に元アプリを終了しても、画像を貼り付けられるよう実体データを公開する。

コピーした範囲の外にある、他のレイヤーや作品の非選択部分を独自形式へ混入させない。既存のコピーが出力する合成対象に従う。

## 座標とAlpha

- 原点はコピー元**キャンバス左上の画素境界(0,0)**。
- Xは右、Yは下へ増える。単位は画像のピクセル。
- 画面表示のズーム、スクロール量、DPI、ウィンドウ座標やDIPを混ぜない。
- レイヤーが移動している場合は、そのオフセットを加えてキャンバス座標へ変換する。
- `origin_x / origin_y`は切り出し画像の画素(0,0)が元キャンバスのどこにあったかを表す。選択した頂点や画像の中心ではない。
- 負の位置を符号付きで扱う。元位置が不明な時は「不明」のフラグにし、既知の(0,0)と混同しない。
- 非矩形選択はRGBA画像として渡す。選択外のAlphaは0、境界では`出力Alpha = 元Alpha × 選択マスクAlpha`。元が既にマスク適用済みなら二重に乗算しない。
- PNGのRGBはストレートAlphaとしてエンコードする。内部が乗算済みAlphaなら正しく変換する。白背景・市松模様を焼き込まない。

例: 元キャンバス1920×1080の(320,180)から400×300を切り出した場合、原点(320,180)、元キャンバス1920×1080、画像400×300。表示が25%でも200%でも値は変えない。

## 同時に公開する形式

一度のコピーで、同じ画像を以下へ公開する。

| 形式 | 内容と用途 |
| --- | --- |
| 登録形式`GVN.Selection.v1` | 元位置・寸法とPNGを一体にした、以下の独自形式 |
| 登録形式`PNG` | 通常のAlpha付きPNG。他アプリが画像として読み取る |
| 標準`CF_DIBV5` | 通常の32bit Alpha付きDIBV5。PNGを読めないアプリとの画像互換 |

既存の`image/png`、`CF_DIB`、`CF_BITMAP`等の公開も、必要な互換性を壊さず維持する。標準形式は位置情報を理解しないアプリでも画像として使える必要がある。**独自形式を追加しても、それに未対応の他アプリが元位置を理解するようになるわけではない。**

PNGは1回だけエンコードする。独自形式に含めるPNGと、標準`PNG`へ公開するバイト列は同一にする。

## 独自形式 `GVN.Selection.v1`

Windowsの`RegisterClipboardFormatW(L"GVN.Selection.v1")`で登録する。数値の形式IDをハードコードしない。

HGLOBALの内容は**64バイトのヘッダー＋PNGの実データ**。多バイト整数はすべてリトルエンディアン。以下のオフセットを固定する。言語標準の構造体サイズやパディングに任せない。

| オフセット | バイト数 | 型 | 値・意味 |
| --- | --- | --- | --- |
| 0 | 8 | bytes | `47 56 4E 53 45 4C 31 00`、ASCIIの`GVNSEL1`＋NUL |
| 8 | 4 | uint32 | `header_bytes = 64` |
| 12 | 4 | uint32 | `version = 1` |
| 16 | 4 | int32 | `origin_x` |
| 20 | 4 | int32 | `origin_y` |
| 24 | 4 | uint32 | `canvas_width` |
| 28 | 4 | uint32 | `canvas_height` |
| 32 | 4 | uint32 | `image_width` |
| 36 | 4 | uint32 | `image_height` |
| 40 | 4 | uint32 | `flags`: bit0だけが「元位置が既知」。既知なら1、不明なら0。他のbitは0 |
| 44 | 4 | uint32 | `png_bytes`、後続PNGのバイト数 |
| 48 | 16 | bytes | 予約領域。全バイト0 |
| 64 | `png_bytes` | bytes | PNG本体。パス、ポインター、Base64文字列ではない |

寸法は1〜65535。右端・下端・バッファ長の計算には十分な桁数を使い、整数オーバーフローと不正な切り出しを防ぐ。アプリ自身の画像容量制限も維持する。元キャンバス寸法が取得できない場合は、偽の値で独自形式を作らず標準画像だけを公開する。

この形式はGVNと自作ペイントアプリの共通仕様で、Windowsやクリスタが元から認識する形式ではない。GVN 0.59.0にはまだ受信機能がなく、GVN側も別途対応する。

### ヘッダー組み立ての参照例

以下はバイト配置を示すPythonの参照例。既存アプリの言語へ移植すること。PNG生成やOSクリップボードへの登録は別の処理。

```python
import struct

def make_gvn_selection(png, origin_x, origin_y,
                       canvas_width, canvas_height,
                       image_width, image_height, origin_known=True):
    header = struct.pack(
        "<8sIIiiIIIIII16s",
        b"GVNSEL1\0", 64, 1,
        origin_x, origin_y,
        canvas_width, canvas_height,
        image_width, image_height,
        1 if origin_known else 0,
        len(png),
        b"\0" * 16,
    )
    assert len(header) == 64
    return header + png
```

## Windowsクリップボードへの公開

- 可能な範囲で画像エンコードと各バッファの準備を済ませてから、既存の有効なowner HWNDで`OpenClipboard`する。
- `EmptyClipboard`はコピー全体で1回だけ。その後、独自形式、PNG、DIBV5などを`SetClipboardData`で登録する。形式を追加する度に空にしない。
- HGLOBALには`GlobalAlloc(GMEM_MOVEABLE, ...)`を使う。`SetClipboardData`成功後はOSへ所有権が移るため、そのハンドルを解放しない。未公開のハンドルだけを解放する。
- クリップボード競合、エンコード失敗、メモリ確保失敗、途中の登録失敗を処理し、必ず`CloseClipboard`する。例外でロックやメモリを残さない。
- 使用中のアプリを強制終了してクリップボードを奪わない。既存の適切な再試行方式があれば利用する。
- 遅延レンダリングを使う場合は、コピー内容を不変のスナップショットとして保持し、コピー後のキャンバス編集と混ざらないようにする。今回の実装では即時に実体データを公開する方式でよい。

DIBV5は標準の124バイトV5ヘッダーと32bit BGRA。BITFIELDSのRGB/AlphaマスクはV5ヘッダー内に置き、その直後にRGBマスクを再度追加しない。RGBはストレートAlphaとし、行の向きは高さの符号と整合させる。既存の正しく動く標準コピー処理があれば再利用する。

WPF/WinForms/Qt/Electron/Rust等のデータオブジェクトを使う場合も、登録形式の実体がこのHGLOBALバイト列になることを確認する。フレームワーク独自のシリアライズヘッダーを付けたり、文字列として変換したりしない。

## 必須の確認

1. 既知座標の矩形をコピーし、ヘッダーの寸法・原点とPNG寸法が一致する。
2. 表示ズーム25%/100%/200%、スクロール、レイヤー移動を変えてもキャンバス座標が正しい。
3. 折れ線/投げ縄選択の外側が透明で、境界と元画像の半透明が保たれる。マスクの二重適用がない。
4. キャンバス左上(0,0)、負の位置、各辺にかかる選択、1px幅等を扱える範囲で確認する。
5. `EnumClipboardFormats`または同等の読み取り検査で、独自形式と標準画像が同時に存在する。
6. 標準PNGと独自形式に含まれるPNGのバイト列が一致する。ヘッダー長は64。
7. 独自形式に未対応の実画像編集ソフトへ、画像として貼り付けられる。Alpha対応先ではAlphaも確認する。
8. 同アプリ内での既存のコピー/貼り付け、選択なしコピー、複数レイヤー等の意味を壊していない。
9. 元アプリ終了後にも画像の貼り付けができる。
10. 失敗時の解放・ロック解除を確認する。試験のために既存作品を上書き・保存しない。

GVN側の対応版がまだ渡されていない段階で「GVNとの実動作確認済み」と報告しない。ヘッダー・PNGの独立検査と、実アプリ間の確認を区別する。関係のない全機能の試験や最適化は繰り返さない。

## 完了報告に含めるもの

- 変更ファイルと、コピー処理のどこへ追加したか。
- 公開した形式名一覧。実行時の数値IDだけで報告しない。
- 合成テスト画像の元キャンバス寸法、切り出し矩形、原点、ヘッダー64バイトのダンプ。
- 標準PNGと独自形式内PNGのSHA256、一致結果。
- Alphaと実際の他アプリへの貼り付け結果。実行できなかった確認は明記する。
- GVN担当へ渡せる、生成したテスト用の64バイトヘッダー＋PNGのサンプルファイル。

実作品の画像をテストサンプルや報告へ添付しない。必要なら単色・半透明・非矩形選択を含む生成画像を使う。

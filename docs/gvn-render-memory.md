# 表示処理と多重起動のメモリ（0.10.2）

頻繁な利用と複数起動を前提に、フィット表示で保持する全画像バッファの重複を減らす。内部の元RGBAは、編集、コピー、保存、OLEのために維持する。

## 表示経路

自動フィットの原寸以外では元RGBAを同期的に借用し、表示範囲のタイルを直接生成する。乗算済みBGRAの全画像バッファと、元寸法のGPUビットマップを保持しない。画像・フレーム・倍率・表示位置・画面寸法・方式が同じなら、生成済みタイルを再利用する。

内蔵11方式の行変換は最大16行・合計1MiB以内。出力タイルは64MiB以内、係数は各軸8MiB以内、中間行は16MiB以内で、計算用作業領域の上限は従来の34MiBから35MiBになる。この数値は画像本体やGPU資源を含むアプリ全体の上限ではない。旧WIC方式は要求された矩形を出力先へ変換し、WIC内部の確保量はこの計数に含まない。

手動ズーム・パンとウィンドウのサイズ変更中は、変換済みの全画像バッファを再利用する。毎回行を変換する方式では、継続操作に追加の時間がかかるためである。サイズ変更の終了/キャンセル後に自動フィットへ戻ると全画像変換バッファを解放する。原寸は従来の直接アップロード経路を使う。画像を閉じた後は元画像用のCPU/GPU資源と表示タイルを解放する。

RGBAから乗算済みBGRAへの変換はx64のSSE2で4画素ずつ処理する。透明/不透明の組を短縮し、半透明は従来の整数式と同じ丸め結果にする。境界の端数はスカラー処理へ戻す。元のRGBAと透明画素内のRGBは変更しない。

## 回帰試験

- 全65,536通りの色×アルファ、RGBの組み替え、非整列アドレス、端数とガード領域を従来の式と比較する。
- 14方式×6表示条件で、RGBA借用と従来の全画像BGRA入力をバイト比較する。縮小、拡大、端数位置、切り出し、50倍、1画素を含む。
- 実Direct2Dで自動フィット、原寸、手動ズーム、サイズ変更、終了後の解放とタイル再利用を検査する。従来の231参照出力・168実描画比較も継続する。
- 専用自動操縦23は53操作・2画面。実Appでフィット/原寸、サイズ変更の終了/キャンセル、Lanczos3設定、GIFの次コマ、RGBAコピーと画像を閉じた後を検査する。
- 保存済みのクリスタ実コピー2種は、独立デコードとの全RGBA一致と再コピーを再確認する。ユーザー素材は配布しない。

全体の結果と対象ソースは[検証記録](gvn-verification.md)、[契約](verification/0.10.2-contract.json)、[自動操縦](verification/0.10.2-autopilot/summary.json)に保存する。

## メモリ比較

生成した3840×2160 JPEGを一画像フォルダから開く。配布済み0.10.1と最終0.10.2を各3組、実行順を交互にして比較した。既定Linear、隠しHWND、OSファイルキャッシュ未消去。各プロセスは描画後2秒待機して測定する。同時ピークや、実写真・全形式の一般的な使用量ではない。

| 起動数 | 0.10.1のプライベートメモリ中央値 | 0.10.2の中央値 | 削減 |
| --- | --- | --- | --- |
| 1個 | 124.28MiB | 92.63MiB | 31.64MiB / 25.46% |
| 4個の合計 | 495.46MiB | 369.49MiB | 125.97MiB / 25.43% |

ワーキングセット中央値は1個で108.98→77.33MiB、4個合計で435.97→309.50MiB。合計ワーキングセットは共有ページを重複計上する可能性がある。比較にはプライベートメモリを主に使う。[全組・各プロセス・ハッシュ](verification/0.10.2-memory-comparison-final/summary.json)を保持する。計時修正前の[最初の比較](verification/0.10.2-memory-comparison/README.md)も別に残し、良い回だけを選ばない。

## 時間の測り方と訂正

従来の`ready_ms`は読み込み結果をAppが採用した時点であり、初回描画の前だった。0.10.1で案内したJPEG139ms/PNG150msを「描画まで」と説明した点を訂正する。過去の生データは変更しない。

0.10.2から`display_ready_ms`で初回Direct2D描画の戻りまで、`first_draw_ms`でその描画呼び出し自体を別に記録する。いずれもプロセス生成・OleInitialize・DWM/実モニタ提示を含まず、総起動時間ではない。旧版には描画時間の同じ計器がないため、この比較からアプリ全体の高速化率は出さない。

単独の新規プロセス各3回で、JPEGの採用完了は[167,260,128]ms、描画まで[499,583,451]ms、描画呼び出し[331.621,322.743,323.038]ms。PNGはそれぞれ[163,131,139]ms、[525,437,448]ms、[362.416,305.207,308.516]msだった。[JPEG](verification/0.10.2-profile/isolated-jpeg/summary.json)、[PNG](verification/0.10.2-profile/isolated-png/summary.json)に全結果を保存する。別の比較試験の単独表示は440〜836ms、4個同時は799〜1284msで、変動も残っている。初回描画の待ち時間は次の最適化対象とする。

CPU計算だけのプローブはデコード済み4K画像で14方式を各3回比較した。Linearの「全画像スカラー変換＋タイル生成」中央値86.09msに対し、RGBA借用は50.70ms、SIMD全画像変換＋タイル生成は66.10ms。GPU初期化、画像デコード、アプリ起動を含まない。継続操作では全画像キャッシュの方が速い条件があるため、実表示では上記の使い分けを行う。[全サンプル](verification/0.10.2-display-cpu.json)、[対象ソースと条件](verification/0.10.2-display-cpu-metadata.json)を参照。

MassiGraの追加起動比較は行わない。次は初回Direct2D初期化の内訳、先読み予算、巨大アニメ・実写真・多ファイル時の上限を調べる。

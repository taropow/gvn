# プレビューを閉じる時の応答性（0.18.0）

ジャンプ画面のデコーダを画面から分離し、読み込み中でもキャンセルや閉じる操作を返す。0.17.0の画面は専用Loaderを所有していたため、破棄時に進行中のデコード終了を待っていた。

## 実装の契約

- AppがJumpPreviewを所有する。最初のプレビュー要求で既存Loaderを1個だけ作り、追加の先読みをせず、キャッシュ予算を0にする。
- 画面は共有サービスと自分用の受信箱を持つ。コールバックは画面、HWND、Appを参照せず、弱参照で生きている受信箱だけへ結果を渡す。画面の破棄後に結果を反映しない。
- 閉じる時はその画面の要求を取り消し、受信箱を空にする。デコードの完了を画面の破棄条件にしない。既に別画面へ切り替わっていれば、旧画面の取消で新画面の要求を止めない。
- 読み込み中に開き直す場合は同じサービスを再利用する。実行中1件と最新の待機1件に制限し、開くたびにスレッドを増やさない。要求番号による古い結果の拒否も維持する。
- ジャンプ画面を閉じた後、Appは250ms間隔でアイドルを確認してサービスを回収する。再び開く時は回収タイマーを止め、画面使用中に最後の所有者を失わない。
- 通常の画像送りには既存の本体Loaderを使う。停止中のプレビューが本体の読み込みを占有しない。

`choose_jump`はAppが保持するサービスを必須引数とする。単体試験用に画面が単独所有する構成は用意しているが、本体の画面終了経路には使わない。

## 検査

修正前の0.17.0と一致する画面部品に、終了を保留できるデコーダを接続した。画面の終了はデコーダ解放後まで返らず、追加した回帰ケースだけが失敗した。[修正前の証跡](verification/0.18.0-before-preview-shutdown-fix/scope.json)を保存する。

同じ回帰ケース本体のSHA256を保持し、Appと同じ所有関係へ変更すると、デコーダ解放前に画面終了が返った。観測値は修正前717.197ms、修正後4.5177ms。ただし前者は監視役がゲートを解放するまでの人工的な待機時間であり、実画像やMassiGraの処理速度比較には使わない。合否の条件は時間比ではなく「デコーダの解放より前に画面終了が返ること」。

関連4項目が成功した。Loader16、ジャンプ画面10、App71ケースと設定応答検査を含む。新しいサービス試験は旧受信箱の解放、最新要求だけの処理、同一ワーカーの再利用、古い画面からの取消を確認する。App試験は保留中のプレビューと通常の画像送りの独立動作、タイマーによる回収を確認する。

専用33/34の249操作・15画面が成功した。34はデコーダ入口を意図的に保留し、実際の画面を閉じ、本体の画像送り、同じサービスでの再オープン、再び閉じてからの解放・回収、新しい通常プレビューを検査する。ゲート解放後は既存の実デコーダで合成素材を読み込む。監視役による強制解放は発生していない。[関連検証](verification/0.18.0-preview-related.json)を参照。

## 残る範囲

実行中のOS I/Oやデコーダ自体を強制中断するものではない。アプリ全体の最終終了では所有ワーカーの終了待ちが残る。縮小専用デコード、巨大アニメのストリーミング、通常の明示オープンと起動時の一覧処理は別作業である。既存の画像展開上限も変えない。

今回の検査は専用ウィンドウステーション内で、合成素材と本体の実コントロールを使う。ComputerUseやグローバル入力は使わず、ユーザーのクリップボードと設定を変更しない。実写真・巨大PSDでの総処理時間や、実モニタ間DPI、外部ソフトの受信を確認したことにはしない。全28項目・71統合ケース・専用34本5,710操作・133画面と配布本体10経路が成功し、この段階は0.18.0として配布した。通常オープンは[0.19.0](gvn-open-preparation.md)で補完した。[最終範囲](verification/0.18.0-preview-lifetime-stage.json)を保存する。設定台帳の完了数は変えず、全体GOALは継続する。

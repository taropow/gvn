# 表示処理の速度・メモリ改善（0.73.0）

普段の画像表示・ズーム・手のひら移動・スクロール・サイズ変更で使う経路を改善した。画質設定や画像のRGBAを変えて速度を稼ぐ方式にはしない。

## 表示用メモリ

原寸以外のフィット・手動ズーム・パンは元RGBAを同期的に借用して、表示タイルに必要な列と行だけを乗算済みBGRAへ変換する。以前の手動表示は元画像と同じ大きさの変換済みBGRAを保持していた。4096×3072なら48MiB、8192×4096なら128MiBの重複を廃止する。画像本体、Undo、読み込みキャッシュ、GPU資源は別であり、この数値をアプリ全体の削減量とはしない。

原寸の直接描画と通常のウィンドウ連続リサイズでは従来の元寸法ビットマップを使う。サイズ変更の終了後は指定方式で再計算し、フィルタ表示へ戻れば全画像の変換キャッシュを解放する。非常に横長の画像などGPUの寸法上限を超える場合も、表示タイルで処理する。

変換行のキャッシュは最大16行・1MiB以内。拡大時はフィルタの端の画素も含め、参照する列だけを変換する。出力タイルは64MiB以内、係数は各軸8MiB以内、縮小の中間行キャッシュは16MiB以内。新しい倍精度の入力行は最大約2MiBで、元画像全体を倍精度へ展開しない。これらはアプリ全体や旧WIC方式内部の上限ではない。

## 高画質フィルタと移動

色とAlphaの4成分をSSE2で並行計算する。各成分のタップ順序、倍精度、乗算後の加算、途中のクリッピングと丸めを保ち、FMAやfast-mathは使わない。縮小では入力行を一度だけ倍精度へ展開し、Lanczosの各タップで同じバイト列を繰り返し展開する処理を減らす。

既定「高速」の平均化縮小は、単位重みのタップを32bitの列加算・64bitの矩形合計で計算する。従来の倍精度計算もこの条件では正確な整数であり、最後の切り捨て除算まで同じ結果を維持する。Alphaを含む中間行のサイズも従来の半分になる。平均化に該当しない拡縮や他の方式は従来の重みを使う。

表示用の丸めは、有限の計算結果について従来の `clamp(lround(value), 0, Alpha)` と同じ結果になる専用処理にした。単に0.5を足す式は境界の直前で誤るため採用していない。画像サイズ変更の透明色は従来の精度を保つ経路を継続し、不透明画像で共用するフィルタ計算だけがこの改善を使う。

同じ画像・コマ・方式・倍率で、タイルが新しい表示範囲を覆えば再計算せず位置だけ変える。手動表示には周囲96pxの余裕を付けるが、64MiBやGPU寸法上限を超える場合は付けない。自動フィット（アニメを含む）にはこの余白を付けない。手動ズーム中のアニメは表示コマが変わるたびに作り直す。

拡縮後の縦横寸法に端数がある場合は、Direct2Dの端の被覆率に差が出ないよう、移動後に従来の範囲で再計算する。原寸表示、方式・倍率・コマ変更、編集時の無効化、端まで移動して範囲を外れた場合にも、それぞれ既存の再計算・更新を行う。

## 検証と計測

`gvn_render_benchmark` は専用の非対話デスクトップに自分のウィンドウを作り、合成RGBAの4096×3072／8192×4096、無補正／高速／高画質、フィット／75%／250%／5000%の24条件を各5回測る。初回描画にはDirect2Dの初期化・アップロード・EndDrawを含む。移動は1回19×11pxを3回実行し平均する。ファイルデコード、アプリ全体の起動、DWM・実モニタへの提示は含まない。全結果と前後の画素ハッシュを保存し、良い条件だけで全体の高速化率は出さない。

同じソースの測定用EXEを残して変更前後を比較する。テストでは全Alphaと色の組、負のローブ・半整数直前直後の丸め、SIMDと逐次計算、非整列行と端数、長い画像の作業領域、実Direct2Dでの再利用有無の画面一致、参照ソフトの既存画素を確認する。実アプリではズーム・手のひら・連続リサイズ・AlphaコピーとGIF/APNGの表示を、専用自動操縦も使って検証する。

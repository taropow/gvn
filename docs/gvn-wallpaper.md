# 壁紙の仕様と実装手順

0.32.0で配置5方式と削除をメニュー・キー/マウスへ接続した。[最終検証範囲](verification/0.32.0-wallpaper-stage.json)では全47検査、本体169件、専用60本10,373操作・224画面が成功し、通常/軽量配布を確認した。壁紙は8ケースを追加し、既存の本体161ケースの本文を維持した。通常GVNと配布本体の各18プロセス86ケース、各68 BMP・独立20,478 RGB画素比較も成功した。6操作を台帳の実装済みへ更新して再照合した。実Windowsの物理壁紙描画と複数モニターの見え方は未確認で、親行の実機未確認判定と全体GOALは継続している。[関連・通常プロセス検証](verification/0.32.0-wallpaper-stock.json)、[配布プロセス検証](verification/0.32.0-package-wallpaper-processes.json)、[初回の関連検証](verification/0.32.0-wallpaper-app.json)も保持する。

[基盤4テストと独立BMP比較](verification/0.32.0-wallpaper-foundation.json)に加え、実Appと通常GVNからも参照40条件・19,950 RGB画素を照合した。基盤・実Appでは4bitパレットと色番号、通常プロセスではBMPのビット数と全RGBも比較した。現在コマ、元Alpha・全コマ・再生情報、選択範囲・Undo・変更状態、読み込み中の別画像への要求を保つことを確認した。通常GVNが生成した68個のBMPは独立した照合でも全20,478 RGB画素が一致した。APNGは既存の独立チャンク合成オラクルを使い、PSDは既知の6画素を持つ16bit合成試料を使った。汎用PSDの独立デコーダー検査を追加したという意味ではない。

## 参照で確認した動作

[MassiGra公式ヘルプ](http://www.massigra.net/massigrahelp/currentver/m_o_wall.htm)と[実測記録](verification/wallpaper-reference-0.45.json)を照合した。公式0.45を専用の非対話デスクトップで9回起動し、40回の壁紙設定要求と生成BMPを採取した。観測器はWindowsの壁紙APIとデスクトップ用レジストリへの変更を仮想化し、AppDataを検査領域へ向ける。元画像・ユーザーの壁紙設定・既存GVN配布版を変更せず、ComputerUse・物理入力を使用しない。

| 操作 | TileWallpaper | WallpaperStyle | BMPの拡縮 |
| --- | --- | --- | --- |
| 中央に表示 | 0 | 0 | 行わない |
| 並べて表示 | 1 | 0 | 行わない |
| 伸縮して表示 | 0 | 2 | 行わない |
| 横幅に合わせる | 0 | 10 | 行わない |
| 縦幅に合わせる | 0 | 6 | 行わない |

5方式とも元の画素数を保つBMPを生成し、配置はWindowsへ渡していた。横長・縦長・正方形でも上記の配置値は同じで、GVN側で幅/高さの固定サイズへ事前に拡縮しない。要求は`SPI_SETDESKWALLPAPER`、フラグは`SPIF_UPDATEINIFILE | SPIF_SENDCHANGE`である。[Windows APIの仕様](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-systemparametersinfow)も参照する。

選択範囲があっても画像全体を使う。RGB入力は24bit BMP、4bitパレット入力は色と番号を保つ4bit BMPだった。PNGのアルファ付き試料では灰色128へ合成された24bit BMPとなり、全551画素が`(色×alpha + 128×(255-alpha))/255`の切捨てに一致した。この参照値は壁紙出力だけへ適用し、GVNが保持する元画像・クリップボード画像のアルファは変えない。

生成した壁紙ファイルがない場合は「壁紙ファイルを削除」が無効になる。画像を閉じた後は配置5項目が無効になり、生成ファイルがあれば削除は有効のままである。削除は確認を表示し、取消では生成ファイルを保持する。確定では配置を中央・タイルなしへ戻し、空の壁紙パスを要求してから生成BMPだけを削除していた。元の入力画像は残る。

[追加の公式メニュー観測](verification/0.32.0-wallpaper-app/reference-menu-checks/result.json)では、配置5項目はいずれも選択前・設定後にチェックが付かないことも確認した。GVNでも配置をラジオ項目にせず、設定操作として表示する。

観測したのは実コマンド、生成ファイル、APIへの要求である。実ユーザーのデスクトップへ適用した際のWindows側の描画や、複数モニター上の物理的な見え方は未検証である。

## GVNの実装契約

- 配置5操作と生成ファイル削除を、既存のアイコン/メニューのデザインに合わせた壁紙サブメニューへ置く。既存の壁紙ショートカットはこのメニューへ接続し、各操作もキー/マウスへ割り当てられるようにする。
- 元画像の全体と現在のコマを使う。選択・Undo・変更状態・再生状態・ファイルの参照先を維持し、入力画像を上書きしない。
- `wallpaper_style`で5方式の値を一元化する。`encode_wallpaper_bmp`は拡縮せず1コマを生成し、不透明入力では余分な画像コピーを避ける。アルファ付き入力は壁紙用の出力だけを合成する。
- 生成物は実際に使用中のGVN設定ファイルに対応した管理領域へ置く。`--settings`を渡した検査では、その領域からユーザーの既定AppDataへ書き出さない。既存の汎用壁紙処理が`settings_path()`を直接使う経路を置き換える。
- 保存・適用・削除の失敗時に、元画像や既存の生成ファイルを失わないようにする。複数インスタンスからの操作、既存の生成物、読込中・アニメ・匿名クリップボード画像を検査する。
- Windows APIの要求は独立した境界にまとめる。専用自動操縦では要求値と生成BMPを検査し、実際のユーザーの壁紙・レジストリを書き換えない。

## 接続済みの管理と操作

「ファイル → 壁紙にする」に配置5方式と削除を置いた。従来の「壁紙にする…」機能へのキー割り当ては、このサブメニューを開く。新しい6操作は個別にキー/マウスへ割り当てられ、既存の機能IDは変更していない。画像がない時は配置5項目、生成物がない時は削除が無効になる。メニューを開く際に状態を再確認するため、別インスタンスによる生成・削除も反映する。メニューの構築ではWindowsの壁紙設定を問い合わせない。

生成先は使用中の設定ファイルと同じ階層の`wallpaper`フォルダーで、ファイル名は新しいGUID付きBMPとする。入力・設定ファイルを上書きせず、管理形式に合う直下の通常ファイルだけを扱う。リパースポイントや無関係なファイルは対象外である。適用成功後に以前の生成物を片付けるが、入力として開いている生成BMPや使用中で削除できないファイルは保持する。

入力保護で意図的に残す場合は通知しない。使用中などの理由で実際に片付けられなかった場合は通知する。通常プロセス検査でこの区別ができず誤通知になる問題を見つけ、状態を区別して修正した。本体の追加ケースでは、入力を保持する操作が無通知で成功することと、別の古いファイルを共有ロックした時には引き続き通知することの両方を検査した。

設定・適用前の配置値と壁紙パスを取得し、適用失敗時に復旧する。復旧にも失敗した場合は新しいBMPを回復用に残す。削除では元のBMPを復旧できるコピーを確保してから設定解除と削除を行い、一部の削除が失敗した場合は削除済みのファイルを先に復元してから壁紙設定を戻す。読み取り専用、共有ロック、途中失敗、復旧失敗、名前付きミューテックスの競合を管理テストで検査した。

Windows用境界は`TileWallpaper`/`WallpaperStyle`と`SystemParametersInfoW`に接続する。管理テストは専用の一時レジストリキーとAPI記録用関数を使い、欠落値・元の型/バイト列・Unicodeパス・解除・要求フラグを確認した。本体テストと専用自動操縦でも壁紙APIを記録用関数へ置き換えている。

通常プロセス検査では、ビルド済みGVNをバイト一致で専用領域へ複製し、実メニュー・ネイティブダイアログ・クリップボードを操作した。x64観測器を専用子プロセスへ入れ、既定のレジストリ/SPI呼び出しを受け取る。壁紙設定と壁紙用ミューテックスは専用領域へ仮想化し、実際のウィンドウ処理を置き換えずに、キューへ送った専用メッセージで先行コマンドの完了を確認する。生成BMP、フラグ3、5配置値、日本語パス、取消、API失敗時の復旧、同じ設定での再起動、入力となった生成BMPの保持、2個の同時起動、別ウィンドウでの削除後のメニュー更新を確認した。18プロセスはすべて通常終了し、意図的なAPI失敗を処理した1プロセスだけ既存の終了コード1、残る17プロセスは0だった。

観測器の初回不備と再検証も記録した。既存の親ディレクトリを作成APIで確認する経路には、変更せず「既存」を返す。INIキャッシュのフラッシュで戻り値0になる扱いは[Windows APIの仕様](https://learn.microsoft.com/en-us/windows/desktop/api/winbase/nf-winbase-writeprivateprofilestringa)へ合わせた。テスト用の完了記録と実API呼び出しも区別して検査する。これらの観測器の修正を理由にGVN本体のテスト条件を緩めていない。

通常プロセスでもユーザーの壁紙・設定ファイル・元画像は変わっていない。確認したのはGVNの既定API経路と要求・生成物であり、Windowsが実デスクトップや複数モニターに描く結果は未検証である。

初回の自動操縦は、新シナリオで確認回答を`YES`/`NO`と記したため、既存のパーサーで取消になった。`Yes`/`No`へ直して再実行し、アプリ・実行ファイル・既存ケースは変更していない。独立画像比較の初回でもPillowのAPNG直接合成経路に差が出たが、既存のチャンク単位の独立合成オラクルと一致することを確認した。両方の初回記録と再検証を保存している。

## 検証順序

1. 参照40条件の配置値、19,950 RGB画素、4bitのパレットと色番号、元Alphaの保持を基盤テストで比較する。
2. 現在コマ・元の全コマと再生情報、不正な画像/コマ/色指定を基盤で確認する。
3. 管理ファイルとWindows APIを接続し、保存/適用/取消/削除/エラーと復旧を検査する。
4. 実Appのメニュー・キー/マウス・画像なし・画像の交代・選択・PNG/PSD/GIF/APNG・Undo保持を確認する。
5. 通常GVNプロセスと専用自動操縦で、同じ設定・管理ファイルの再起動とAPI要求・画素を検査する。
6. 全体回帰と配布版を検証し、仕様・作業リスト・台帳の完了判定を更新する。

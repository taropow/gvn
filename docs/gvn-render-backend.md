# 初回描画と描画先の選択（0.10.3）

小窓の初回表示と多重起動を軽くし、大きな画面での連続描画も維持する。表示用タイルの計算、元RGBA、クリップボードや保存の内容は変更しない。

## 選択の規則

初めて描画先を作る時、クライアント領域が2,097,152画素以下ならDirect2Dのソフトウェア描画を使う。これより大きければDirect2Dのシステム選択を使う。システム選択は利用可能ならハードウェアを使い、利用できなければソフトウェアへ戻る。[Microsoftの描画先種別](https://learn.microsoft.com/en-us/windows/win32/api/d2d1/ne-d2d1-d2d1_render_target_type)に従う。

小窓から大きくした時はシステム選択の描画先へ切り替える。ウィンドウを手でサイズ変更している間は生成の負荷を避け、サイズ変更の終了またはキャンセル後の描画で切り替える。大画面から小さく戻した場合は既存の描画先を再利用し、境界付近で切り替えを繰り返さない。背景変更やデバイス再生成で作り直す際は、現在の寸法で改めて選択する。

切り替え時にCPUの元画素・計算済みタイルを保持し、描画先に依存するビットマップ・ブラシだけを再生成する。画像を閉じた後の資源解放と、手動ズーム中の変換キャッシュの方針は[0.10.2の契約](gvn-render-memory.md)を維持する。この選択のための設定操作は不要。

画面とキャプチャ用の描画先は、最大ビットマップ寸法が異なる場合がある。それぞれ実際の描画先の上限を使い、直接アップロードの一辺は最大16,384画素までにする。これを超える横長/縦長画像は、原寸でも見えるタイルだけを生成し、全体を巨大なビットマップへ載せない。

## 初期診断

同じ`Renderer`へ工程別の計器を追加した。通常の描画では時計を読まず、診断時だけファクトリ、描画先、ブラシ、サンプリング、転送、背景、描画の時間を採取する。転送工程には、原寸経路の全画像変換が含まれる。描画工程は`EndDraw`の戻りまでで、実モニタへの提示完了ではない。

生成4K JPEGを事前デコードし、隠した専用HWNDへ描画した。幅1000/3840、画像なし/画像あり、システム選択/ソフトウェアを各3つの新規プロセスで交互に実行した。各プロセスは初回、同じ内容10回、手動パン21回を描き、全24プロセス・768描画を記録する。画像デコード・プロセス生成・Appの初期化は対象外。通常デスクトップ上の自プロセスの隠しウィンドウだけを作り、他のウィンドウと入力を操作しない。

| 条件 | システム選択の初回中央値 | ソフトウェアの初回中央値 | 同じ内容の反復中央値（システム / ソフトウェア） |
| --- | --- | --- | --- |
| 1000×690、画像なし | 295.23ms | 26.13ms | 0.423 / 0.228ms |
| 1000×690、4K画像 | 341.20ms | 73.88ms | 0.396 / 0.302ms |
| 3840×2649、画像なし | 281.53ms | 42.80ms | 0.364 / 8.987ms |
| 3840×2649、4K画像・原寸 | 341.30ms | 59.69ms | 0.426 / 10.457ms |

このPCでは初回の描画先生成が約240〜320msを占めた。大画面の繰り返し描画ではソフトウェア側の負荷が増えるため、全サイズを一律に切り替えない。[全サンプル・測定時ハッシュ](verification/0.10.3-initial-render-probe/summary.json)と当時のソースを保存した。初期診断のバイナリは最終版と区別し、最終アプリの比較は別に保存する。

## 回帰で確認する内容

ネイティブ描画試験は実際の描画先を作り、2,097,152画素の境界、サイズ変更中の延期、終了後の切り替え、縮小時の再利用、背景再生成、CPUタイルとRGBA保持を確認する。通常の再描画でファクトリと描画先を作り直していないことも、工程値で検査する。

初回の回帰で65,535×2画像のキャプチャが失敗した。HWND側の寸法上限をキャプチャ側にも使っていたことを修正し、同じ素材を自動/ソフトウェア/システム選択の全経路で画面描画とキャプチャに通す。原寸の見えている128画素も独立に照合する。

専用自動操縦24は実Appで小窓→大窓→小窓を操作し、サイズ変更中の延期、切り替え後のRGBAコピー、アニメのコマ送り、画像を閉じた後の市松表示を通す。既存の画素参照、設定、自動操縦も継続する。隔離ステーションのキャプチャと実モニタの表示は別の検証範囲とする。

`--profile`は採用完了、初回描画の戻り、工程別時間、描画先種別を記録する。`--profile-empty レポート.json`は画像なしの初回市松描画を同様に測る。診断モードは設定を保存しない。プロセス生成、OleInitialize、DWMを含まないため、総起動時間とは呼ばない。MassiGraの追加起動比較は行わない。

## 最終アプリの測定

最終0.10.3と配布済み0.10.2を、生成3840×2160 JPEGの一画像フォルダで比較した。各条件3組、旧/新の実行順を交互にする。既定Linear、通常サイズの隠しウィンドウ、OSファイルキャッシュ未消去。全組と各プロセスの値を保存し、良い回だけを選ばない。

| 起動数 | プライベートメモリ中央値（旧 → 新） | 削減 | 初回描画戻りまでの中央値（旧 → 新） |
| --- | --- | --- | --- |
| 1個 | 92.18 → 43.69MiB | 52.60% | 477.0 → 215.0ms |
| 4個 | 370.51 → 175.25MiB | 52.70% | 805.5 → 525.0ms |

メモリは各プロセスが描画後2秒待機して採取した値で、同時ピークではない。4個の時間は全12プロセスの中央値、メモリは各組4個合計の中央値である。1個のワーキングセット中央値は77.33→59.98MiB、4個合計は309.46→239.85MiB。共有ページの重複計上があるため、ワーキングセットの合計とプライベートメモリを区別する。[全組・ハッシュ・条件](verification/0.10.3-comparison/summary.json)を参照。

別の単独プロセス測定では、JPEGの採用完了[171,125,139]ms、描画まで[244,196,215]ms、描画呼び出し[73.2263,71.8784,76.2845]ms。PNGは採用完了[162,110,121]ms、描画まで[231,187,210]ms、描画呼び出し[68.9179,77.1091,88.8884]msだった。

画像なしの市松表示は、App内の計時開始から描画戻りまで[143,123,93]ms、描画呼び出し[34.5874,28.7425,27.273]ms。プライベートメモリは約6.7〜6.9MiB、ワーキングセットは約21.3〜21.5MiBだった。旧版には同じ空画面用の診断引数がなく、空起動全体の新旧比較には使わない。

時計は`App.started`初期化時からで、それより前のメンバー生成、プロセス生成、OleInitialize、DWM/実モニタ提示を含まない。総起動時間や全環境の保証値とは呼ばない。[全値と工程](verification/0.10.3-profile/summary.json)を参照。実写真・大きい画面・巨大アニメ・実DPIの評価は継続する。

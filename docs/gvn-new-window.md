# 別ウィンドウへの画像の受け渡し

0.41.0へ画素スナップショットのDPI引継ぎを配布反映済み。

「画像をクリップボード経由で送る」「クリップボードの画像を貼り付け」は、画像に定義済みの縦横DPIを新しい画面へ引き継ぐ。回転による縦横の入れ替え、選択画像、表示中のアニメのコマに対応する。元画像のUndo・選択・再生状態は保つ。

共有メモリの形式2では、有限かつ正の縦横解像度をRGBAの前へ格納する。解像度未定義の画像・空・ファイル指定は従来の形式1を維持する。受信は両形式に対応し、不正な解像度や長さを画素配列の確保前に拒否する。読み取り専用ハンドルの明示継承も維持する。

[今回の確認記録](verification/0.41.0-new-window-dpi-related.json): 基盤15件、本体3件、通常GVNの実親1・子2。144.5×288.25DPIの合成透過画像を回転して送信・貼り付けし、子の情報欄に288.239×144.501DPIと表示され、再コピーPNGの解像度と2×3の全RGBAも一致した。PNGの整数のメートル当たり画素数による丸めを含む。ユーザーのクリップボード・ウィンドウは使っていない。外部編集ソフトの受信、物理モニターのDPI・前景動作までの確認ではない。以下は0.26の記録。

0.26.0で「もう1つ起動」の空・元ファイル・画像送信・貼り付けを区別し、Alphaと表示元を保持した。多重起動OFFと前回ファイル再開ONでも独立した画面になる。全37項目・本体125/設定39/受け渡し基盤11件、専用48本8,189操作・184画面、通常/軽量配布の各10経路と実プロセス9+13+3+別起動6ケースが成功。保存済みクリスタ2試料の全RGBAと再コピーも成功。[最終検証範囲](verification/0.26.0-new-window-stage.json)を保存した。機能5行を実装済みに更新し、設定の残差分と全体GOALは継続する。

2026年10月19日。0.26.0で関連・全体回帰と配布検証が成功した。全体GOALと設定の残差分は継続する。

## 操作の契約

| 操作 | 新しい画面の内容 | 元の画面とクリップボード |
| --- | --- | --- |
| 空のウィンドウ | 画像なしの市松模様。前回ファイルを再開しない | 元画像とクリップボードを保つ |
| 現在のファイルを開く | 現在表示している画像の元ファイルを読み直す。未保存の加工は渡さない | 元画像、選択、Undo、進行中の読み込みを保つ |
| 画像をクリップボード経由で送る | 表示中のコマ。選択があれば選択範囲。加工後の画素とAlphaを保つ匿名画像 | 通常の画像コピーとしてOSクリップボードへ公開し、元画像とUndoを保つ |
| クリップボードの画像を貼り付け | 実行時のクリップボード画像をAlpha付きの匿名画像として開く。対応画像へのフルパスもGVNの通常貼り付けと同じ経路で受け取る | クリップボードを上書きせず、元画像を保つ |

4操作は多重起動OFFでも独立した画面を作る。対応する既存プロセスへ転送して元画像を置き換える動作にはしない。元ファイルのない画像では「現在のファイル」を実行しても画像の一時ファイルを作らない。読み込み中は移動先ではなく表示元を使用する。新しい画面にも通常のキー/マウス・表示・アニメーション設定を適用する。

## 参照で確認した範囲

[公式ヘルプ](http://www.massigra.net/massigrahelp/currentver/m_f_newwnd.htm)の4操作を、[公式0.45の実観測](verification/new-window-reference-0.45.json)と対応付けた。生成した日本語・空白のあるPNGだけを使用し、所有する親プロセスと、その親が生成した同一実行ファイルの子プロセスだけを操作した。

空の画面、通常ファイル、加工後の元ファイル、加工画像の送信、選択範囲の送信、クリップボードの貼り付けの6ケースを観測した。加工後に「現在のファイル」を選ぶと加工前の画素と元パスになった。送信と貼り付けは「名称未定-1」の匿名画像となり、選択範囲は2×3の画素で一致した。送信だけが実行前のクリップボードを更新した。参照での透過・アニメーションの全組合せまで確認したという意味ではない。

最初の観測スクリプトでは、メニューバーの準備、項目名の曖昧一致、子ウィンドウのタイトル条件に誤りがあった。失敗記録と当時のソースを保持し、製品の機能不良や成功の証拠として使用しない。成功した6ケースでは画素と実際のファイル名コピーを照合した。

## 受け渡しの基盤

実行時に内容を確定し、匿名の共有メモリを読み取り専用のハンドルとして子に渡す。一時画像ファイルを保存せず、起動中にOSクリップボードや元画面が変化しても、その後の内容へ取り違えない。RGBAをそのまま転送し、透明画素のRGBも含めて維持する。元ファイルを開く操作は画像の加工結果を転送しない。

ハンドルの継承は[MicrosoftのAPI仕様](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)の明示リストを使用し、共有スナップショットだけを対象にする。[ファイルマッピング](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-createfilemappingw)とプロセスのハンドルは使用後に解放する。子は呼び出し元と同じウィンドウステーション・デスクトップで作り、専用試験ではユーザーのデスクトップへ表示しない。

## 作業と検証の順序

1. 検証済み: 公式の6ケースと実コマンド40241〜40244を固定した。
2. 検証済み: [受け渡し基盤11件](verification/0.26.0-new-window-foundation.json)。空・ファイル・画像の実子プロセス3件、Alphaの全RGBAと透明画素のRGB、送信後の元データ変更、読み取り専用の共有、不必要なハンドルの継承防止、設定ファイルの保持、起動失敗時の後始末を確認した。
3. 関連範囲で検証済み: 実メニュー・キー/マウスの機能カタログ・通常GVNの起動経路へ4操作を接続した。専用4本759操作・11画面が成功し、新48は78操作でF12・中クリック・匿名画像・Undo・Alphaを確認した。自動操縦では新規起動境界を捕捉し、実プロセス検査とは区別する。
4. 関連範囲で検証済み: [本体125件・設定39件・基盤11件と設定画面](verification/0.26.0-new-window-app-related.json)。元画面のUndo/選択/Alpha、読み込み中の表示元、アニメの現在コマ、ZIPと匿名画像、起動失敗と非対応クリップボードを確認した。既存の123メソッド本体をバイト単位で保持する。
5. 関連範囲で検証済み: [通常GVNの初回6ケース](verification/0.26.0-new-window-process-first.json)と、正式なCTest経路の6ケースが成功した。多重起動OFF・前回ファイル再開ONでも4操作は独立し、元パスと全RGBAを保持する。正式経路では子の通常終了後も2つの設定を保持した。最初のCTestではCP932のログ出力が画像タイトルの記号を扱えず失敗したため、テスト起動をUTF-8へ指定した。製品ソースや画素の条件を変えず、失敗記録も保持する。
6. 検証済み: 全37項目・全48本の回帰と保存済みクリスタ2試料、通常/軽量配布と通常終了後の設定を再検査し、台帳の5行を更新した。

基盤の成功は、通常のGVN画面の4操作や外部編集ソフトとの連携の完了を意味しない。
